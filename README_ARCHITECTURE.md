# README_ARCHITECTURE

## Цель
По одному объявлению определить:
- представлены ли в тексте другие микрокатегории;
- продаются ли они как самостоятельные услуги;
- нужно ли создавать дополнительные черновики;
- какой текст предложить для каждого черновика.

## Пайплайн
### 1. Retrieve
`dictionary_matcher.py`

Что делает:
- нормализует текст;
- ищет совпадения по `keyPhrases`;
- допускает мягкое phrase matching через `SequenceMatcher`;
- формирует список `CandidateMatch`.

Почему отдельно:
- это объяснимый и дешёвый этап;
- он резко уменьшает число кандидатов для LLM.

### 2. Feature extraction
`feature_extractor.py`

Для каждого кандидата считаются:
- standalone markers: `отдельно`, `самостоятельно`, `по отдельности`, `только`;
- bundled markers: `под ключ`, `включая`, `в составе`, `комплексно`;
- число предложений, где фраза микрокатегории встречается рядом с нужным маркером;
- совпадает ли кандидат с исходной микрокатегорией;
- rule score и предварительное rule decision.

### 3. Candidate ranking
`rule_scorer.py`

Смысл:
- сохранить приоритет сильных rule-кандидатов;
- не потерять слабые, но потенциально значимые категории;
- верифицировать не только shortlist, но и разумный набор `llmCandidates`.

### 4. Verify with Qwen 3
`qwen_client.py` + `prompts.py`

`Qwen 3` используется как semantic verifier для candidate set.

Модель получает:
- исходное объявление;
- текущую исходную микрокатегорию;
- кандидатные `mcId`;
- matched phrases;
- короткие explainable признаки.

Verifier отвечает коротким JSON:
- `mcId`
- `isStandalone`

Дополнительно:
- в запрос автоматически добавляется `/no_think`;
- `max_tokens` резко снижен;
- применяется жёсткий timeout;
- если модель даёт слабый отрицательный ответ, но rule-сигнал очень сильный, срабатывает `hybrid-override`.

### 5. Generate drafts
`draft_generator.py`

Для подтвержденных микрокатегорий `Qwen 3` генерирует узкий текст черновика на отдельном втором шаге:
- только под целевую услугу;
- без лишних bundled-услуг;
- в JSON-формате.

Интерфейс сознательно разделён на 2 шага:
1. `Определить категории`
2. `Сгенерировать draft`

Это уменьшает задержки и соответствует продуктовой логике: сначала убедиться, что split действительно нужен, потом уже тратить токены на генерацию.

## Почему архитектура именно такая
- Высокий precision важнее recall.
- Словарь и правила хорошо отсекают явный шум.
- LLM лучше всего работает как semantic verifier на малом числе кандидатов.
- Такое разделение легче дебажить и калибровать.
- Исходная микрокатегория не должна дублироваться среди дополнительных draft-категорий.

## Отказоустойчивость
- сначала пробуем локальный HTTP API;
- затем fallback на `llama-cli.exe`;
- затем rule fallback, если модельный JSON неполный или отсутствует;
- для сильных rule-сигналов включён `hybrid-override`;
- в интерфейсе явно показываются `transport`, `timeout` и `source`.
